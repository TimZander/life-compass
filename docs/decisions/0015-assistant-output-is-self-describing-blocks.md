# 0015 — Assistant output is self-describing blocks, one per question group

- **Status:** Proposed
- **Date:** 2026-08-07

## Context

[0007](0007-clipboard-is-the-airgap.md) makes the clipboard the only channel between this
application and an assistant. A prompt goes out, an interview happens somewhere else, and
structured output comes back. `0007 · C4` requires that output to carry a version, so that a
prompt generated by an older build produces something the importer either recognises or
rejects cleanly rather than half-parses. Nothing recorded what the output looks like.

Two interface decisions taken while
[#15](https://github.com/TimZander/life-compass/issues/15) was broken into phases narrow
what this has to specify. The bridge is off by default and enabled from its own page — the
shape [#25](https://github.com/TimZander/life-compass/issues/25) gave backup — and once on,
each question grows a copy button and a paste button.

The second of those is not symmetric with the first. Writing the clipboard is free; reading
it needs a permission that Android Chrome prompts for and Safari gates behind its own UI. So
the agent page also carries a plain box to paste into, and that box — not the per-question
button — is the general mechanism. Anything the reader has in hand must be droppable into it
and land in the right place, or a browser that declines the permission loses the feature
rather than a shortcut.

That is the requirement that shapes everything below: **output has to say what it is, with no
surrounding context to help.**

## Options

**O1. Reuse the export envelope from [0009](0009-encryption-is-an-opt-in-add-on.md).**
*Rejected.* It already carries a format, a version and a payload keyed by identifier, so the
temptation is obvious. But `restore` **replaces** the whole store in one transaction
(`0009 · C7`), and assistant output is a partial merge that must never overwrite silently
(`0007 · C3`). Two opposite semantics behind one `format` string is a trap laid for whoever
reads the code next, and the refusal machinery is cheap to have twice.

**O2. One document that names its scope** — a group, a day, or a whole compass. *Rejected.*
It sounds like the general answer and costs the most: three scope kinds to define, rules for
how a day's scope relates to the groups inside it, and — since a day's reply plainly contains
several things — a list shape at the top level that a later version would have to grow into.

**O3. Self-describing blocks, one per question group.** *Chosen.* Everything O2 wanted comes
from the smallest unit plus the fact that text can contain more than one block.

## Decision

**A block answers exactly one question group, and names which.** A day's reply is several
blocks in one paste; a compass-level synthesis is more of them. There is no list shape in the
format because the pasted text is the list, and no day or compass scope because neither is a
thing the store holds — the store holds groups.

This is what makes "an entire day collected and returned in one exchange" an ordinary use of
version 1 rather than a future addition. Compare `0009 · C6`, which took the opposite lesson
from the same instinct: growing an envelope with an optional field for a consumer that does
not exist yet is speculative machinery, but choosing a top-level shape that does not need to
change is free.

**Blocks are found by their content, not by their fence.** The importer scans pasted text for
fenced code blocks, parses each as JSON, and keeps the ones whose `format` matches. Requiring
a particular info string would be requiring an assistant to be reliable about something they
are demonstrably not — asked for ` ```life-compass ` they will write ` ```json ` — and the
scan is what lets several blocks, and the prose between them, arrive together.

**A block, in full.** This list is authoritative:

- `format` — `"life-compass/agent-answers"`. Distinct from `"life-compass/answers"`, which is
  a backup and means "replace everything".
- `version` — the BLOCK's shape, and moves only when this list changes. A schema edit, a new
  worksheet or a retired question are ordinary content and do not touch it. Same rule
  `0009` gives the envelope.
- `group` — the question's identifier, e.g. `day1.chapters`. Declared in TypeScript rather
  than derived from the prose around it
  ([0004](0004-prose-in-markdown-questions-in-typescript.md)) and frozen once used
  ([0011](0011-question-identifiers-are-frozen-and-registered.md)), which is what makes it
  safe to put in a document that leaves the application and comes back later.
- The answers, in one of three shapes chosen by the question's kind:
  - `answer` — a string, for a `single`.
  - `fields` — identifier segment to string, for a `group` or a `sentence`. A sentence's
    segments are its gap names, which are already its field identifiers.
  - `instances` — an ordered array, for a `repeat`. Each entry is `{ id, fields }`.

**The block does not restate the question's kind.** `questions.json` already says it, and two
copies of one fact can disagree — the failure this repository has now shipped twice. The
importer looks the group up and knows which shape to expect; a block whose shape does not
match its group is refused.

**Instance identity travels in the prompt and comes back echoed.** An assistant cannot invent
the identifiers [0013](0013-instance-identity-for-rendered-slots.md) mints, and it must not:
position as identity is the failure `0011` was written to prevent and `0013` rejected as O1.
So the prompt carries the identifiers of the instances that exist, and the block returns them
per instance.

Carrying them costs nothing against `0007 · 2`, which defaults prior answers to off. **An
instance identifier is structure, not content** — a UUID reveals nothing about what somebody
wrote — so it travels whether or not the reader opted their answers in.

A group nobody has written to has no identifiers yet, because `0013` mints them on first
write. Then:

- An `id` naming an instance the store holds is an answer **to that instance**.
- An `id` the store does not hold, or an entry with none, is a **new instance**, minted at
  import in the order the block gives, bounded by the group's `max`.
- Position is never a storage key. It orders new instances at the moment they are created,
  which is what `0013` already does with rendered slots, and nothing reads it afterwards.
- An identifier a block supplies is validated by the same rules `keys.ts` applies to its own:
  a block cannot write an order that `keys.ts` would refuse to write.

**A block never reorders what exists.** The order is the reader's. New instances append.

**Refuse only what is newer**, exactly as `readEnvelope` does and for the reason its comment
gives: a block from an older version is a problem for the day a second version exists, and
that day arrives with blocks already in the wild to migrate from. Refusing the future is the
part that has to be right now, because a block this build cannot understand is one it must
not guess at.

**Nothing records which question registry a block was generated against.** `0009 · C6`
removed exactly that field from the export envelope and explained why: a digest of a *set*
cannot answer a question about an individual key, and `0011 · C2`'s registry already answers
it per key and permanently.

**A block pasted at a question it does not answer is routed, and says so.** The block names
its group, so where it belongs is not ambiguous, and refusing a paste whose intent is plain
would be pedantry. The reviewing surface names the group it landed on, because routing
somewhere silently is the part that would be surprising.

**Deliberately not in the contract:**

- **Prose around the block.** Assistants explain themselves. That is ordinary, and the scan
  discards it rather than treating it as a defect.
- **Checklists.** They are readiness ticks the reader works through, not questions an
  assistant answers on their behalf. A block naming a `checklist` group is refused.
- **Anything that deletes.** There is no way to express "remove this answer". An assistant
  proposing additions and changes is the whole of it.

## Consequences

**C1.** A whole day comes back in one paste at version 1, and so does a compass-level
synthesis. Neither needs a format change, which is the point of choosing the unit small.

**C2.** The general paste box accepts anything, so the per-question paste button is strictly
additive. A browser that never grants clipboard read costs its reader a tap, not a feature —
which matters because `0007`'s argument is about a choice being real, and a feature available
only where a permission is granted is a choice somebody else made.

**C3.** Prompts carry instance identifiers even when no answers travel. The generator must
therefore be explicit that it is doing so, since `0007 · 1` requires the literal payload to be
previewed: the reader sees the UUIDs. Better that than a preview which is not what is sent.

**C4.** Validation cannot write, structurally, as in `import.ts` — the function that reads a
block has no store to reach. "Never partially imports" stays a property of the design rather
than a promise about statement order.

**C5.** Every refusal says what was wrong **and** that nothing on the device changed. The
existing `Refusal` union is the model, and the kinds this needs are its own: an unknown
format, a newer version, a group not in the registry, a shape that does not match its group's
kind, a checklist, an instance identifier `keys.ts` would refuse.

**C6.** Two formats now exist that both carry answers. Whoever changes one must decide about
the other deliberately — and they are versioned separately on purpose, because the day one
needs to move is not the day the other does.

**C7.** A group with no answers stored still has a usable prompt: no identifiers travel, and
every instance comes back new. The first exchange with an assistant is the common case, not
the edge one, and it must not be the awkward path.
